# 第5章 マルチエージェント

この章を終えると、エージェントを分割すべきかを判断でき、分割するなら「どこをモデルの
裁量に任せ、どこをコードで固定するか」を理由付きで決められるようになります。
ハンズオンでは専門エージェントを 1 体追加します。

## 5.1 概要

### 5.1.1 マルチエージェントとは

1 体のエージェントにすべてをやらせる代わりに、役割ごとの専門エージェントに分けて
連携させる構成です。役割を分けると、それぞれのシステムプロンプトを短く保て、
役割に見合ったモデルを個別に選べるようになります。

### 5.1.2 分割は手段。まず疑う

1 体で足りる処理を分割すると、遅く・高く・デバッグ対象が増えるだけです。
「マルチエージェントにしたい」が目的化した案件で「この規模なら 1 体で十分です」と
言えることも技術のうちです。

分割のサインは症状で判断します。

- システムプロンプトが長大化し、どの指示がモデルの挙動に影響しているか分からない
- 全工程に上位モデルを使っていてコストが下げられない
- 「検索の質」と「統合の質」を別々に改善したいのに、両方が 1 つのプロンプトに
  混ざっていて片方だけを変えられない

責務が違い、必要な能力（= モデル）が違うなら分ける。組織の役割分担と同じ理屈です。

## 5.2 実装のポイント

### 5.2.1 この構成とモデル割り当て

```
依頼 → Orchestrator (Sonnet) ─ investigate ツール → SearchAgent (Haiku) ─ web_search
              │
              └→ 報告完成後、コードが ReviewAgent (Sonnet) を必ず 1 回実行
                 revise 判定なら修正を 1 回だけ
```

- Orchestrator — 観点への分解と統合。判断を伴うので上位モデル
- SearchAgent — クエリ整形と事実抽出だけの定型処理。軽量モデルで足りる
- ReviewAgent — 出典欠落・推測混入の検出。見逃しが信頼性に直結するので上位モデル

役割ごとに理由を付けてモデルを選ぶ。これがコスト最適化の実体です。
Haiku と Sonnet の単価差はおよそ 3〜5 倍あるので、全員に Sonnet を配ると
費用はそれだけで数倍になります。

### 5.2.2 agents-as-tools

Orchestrator から SearchAgent を呼ぶ仕組みは単純です。`search_agent.py` では
エージェントを丸ごと `@tool` で包んで関数にしています。Orchestrator から見れば
SearchAgent はただのツールです。

したがって第3章の規約がそのまま適用されます。docstring は 3 節構成、
「観点を 1 つだけ渡すこと」という使い方の制約まで docstring がモデルに教える。
エージェント分割はツール設計の応用問題です。

Strands の他パターンとの使い分け:

- **agents-as-tools** — 上位が判断しながら委任する。まずこれ
- **Graph** — 手順が固定のパイプライン。分岐・並列を宣言的に固定したいとき
- **Swarm** — エージェント同士の対等な協調。コスト予測が難しく、最後の手段

### 5.2.3 裁量とコードの境界 — この章の核心

SearchAgent と ReviewAgent は呼ばれ方が違います。

- SearchAgent は**ツール**。何回・どの観点で呼ぶかはモデルの裁量。
  依頼ごとに最適な分解が違うから、固定しないことに LLM を使う価値がある
- ReviewAgent は**コードが必ず 1 回実行**。ツールにするとモデルが
  「今回はレビュー不要」と判断した瞬間に検証がスキップされる
- 修正回数も**コードで 1 回に固定**。「revise が出る限り修正」にすると
  コストとターン数の上限が読めなくなる

迷ったときの判定基準はひとつ。その工程がスキップされたとき誰かが困るか。
困るならコードで固定、困らないなら裁量に任せる。

先に読むファイル:

- `orchestrator.py` — 冒頭コメントの処理フローと「修正 1 回」の理由
- `search_agent.py` — エージェントのツール化
- `review_agent.py` — VERDICT 行のパース。判定不能のときは revise と同じ扱いにする設計
  （「問題なし」と同じ扱いにしたら、パースに失敗しただけで報告が検証されないまま通ってしまう）

## 5.3 【ハンズオン】PricingAgent を追加する

価格の比較表づくりに特化した専門エージェントを追加し、Orchestrator に接続します。

`07-full-app/src/agents/pricing_agent.py` を新規作成:

1. `build_pricing_agent_tool(settings)` を実装する（`search_agent.py` と同型）
2. モデルは search ロール（軽量モデル）を使い、理由をコメントに書く
   （ヒント: 表への整形は定型処理か、判断を伴うか）
3. `web_search` ツールを持たせ、`build_guards(settings, role="pricing")` を付ける。
   ガードなしのエージェントを作らないこと
4. システムプロンプトで「価格だけを調べ、Markdown の比較表で返す。確認できない
   セルは『不明』。出典 URL を表の下に列挙」と指示する
5. ツール名は `compare_pricing(companies: str) -> str`。docstring は 3 節構成で、
   「含まないもの」に価格以外（機能・評判）を調べないことを明記する

`orchestrator.py` の変更は 2 箇所:

6. `tools=[...]` に `compare_pricing` を追加
7. システムプロンプトに「価格の比較が求められたら compare_pricing を使う」旨を 1 文追加

変えてはいけないこと: ReviewAgent をツールにしない。既存テストを壊さない。

```bash
uv run --project 07-full-app pytest 05-multi-agent/verify -q
```

```bash
cd 07-full-app && uv run pytest -q
```

両方通れば合格です。余裕があれば、mock プロバイダのまま
「Acme と Globex の pricing を比較して」で比較表が返ることを確認してください。

## 5.4 まとめ

マルチエージェントの設計判断は、分けるかどうかよりも「分けた後にどう呼ぶか」に
表れます。スキップされたら困る工程はコードで固定し、依頼ごとに最適解が変わる工程だけ
モデルの裁量に残す。**裁量とコードの境界を理由付きで引けること**が、この構成を
案件で説明できるかどうかの分かれ目です。

追加した PricingAgent も含め、この結線が壊れていないことは人手で確かめ続けられません。
次章で、LLM を呼ばずにそれをテストする方法を身につけます。
