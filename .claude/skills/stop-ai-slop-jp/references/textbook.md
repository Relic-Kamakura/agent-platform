# 技術教材モード

対象は `NN-*/README.md` と、学習者が読む Python ファイル（`exercises/` の TODO コメント、
章直下スクリプトの docstring、`solutions/` の説明コメント）。

読者は AWS 経験ありのエンジニアで、エージェント開発は未経験。進行役なしの非同期自習で読むため、
分からない語があっても聞ける相手がいない。**「読めば分かる」ではなく「読み違えようがない」**を基準にする。

判断に迷ったら置き換える。残す理由が思いつく比喩ほど、書き手にだけ自明な語である可能性が高い。

## 1. 比喩・擬人化

例外なく置き換える。起きていることを、そのまま書く。

| 書かない | 書く |
| --- | --- |
| revise に倒す | revise 扱いにする |
| 静かに壊れる | 例外は発生しないが、品質が下がる |
| エージェントが壊れる | エージェントが誤った動作をする |
| 例外を握りつぶす | 例外を捕まえて何も返さない |
| 被害を頭打ちにする | 被害を一定以下に抑える |
| 中身は素通し | 中身は制限されない |
| 履歴が膨らむ | 履歴が長くなる |
| ツールを束ねる | ツールを 1 つにまとめる |
| バッチに逃がす | バッチに移す |
| 〜と地続き | 〜とつながる領域 |
| 〜の受け皿 | 〜に対処する |

同じ扱いをする語: 刺さる / 効く / 寄せる / 潰す / 生やす / 剥がす / 掴む / 乗っ取る / 増殖 /
事故 / 土台 / 収まる / 切り替わる。

動詞の口語は次に統一する。

| 書かない | 書く |
| --- | --- |
| イベントを流す | イベントを渡す |
| エンドポイントを叩く | エンドポイントを呼ぶ |
| テストを回す | テストを実行する |
| エージェントを走らせる | エージェントを実行する |
| 読むのも近道です | 読むと分かりやすくなります |

## 2. 界隈でしか通じない省略

一般語に置き換えるか、初出で 1 回だけ補足する。

| 書かない | 書く |
| --- | --- |
| このリポジトリの型（形式の意味） | このリポジトリの形式 |
| 生 HTML | 取得した HTML |
| 素の関数 / 素の性能 | 元の関数 / モデル単体の性能 |
| 引数を束縛する | 引数を固定する |
| エージェント同士の結線 | エージェント同士の呼び出し |
| 修正パス | 報告の修正 |

「型」は Python の型と紛らわしいので、形式・パターン・仕組みのどれかに置き換える。
一般に通用する技術用語（指数バックオフ、冪等、モック、フォールバック）はそのまま使う。

## 3. 見出し

見出しは「読者が何を知りたくてここを読むか」で書く。

- 悪い: 失敗の倒し方 / リトライの範囲 / 暴走の起き方 / CDK 側 / 何を解決するか
- 良い: 判定を取得できなかったとき / どの失敗をリトライするか / 上限が無いと何が起きるか /
  CDK 側で定義するもの / プロンプトキャッシュが解決する問題

命題型（「〜は〜だ」）と擬人化（「1 リクエストの一生」）も使わない。
テーマの名前（名詞句）か、読者の疑問の形にする。

## 4. 説明なしの初出用語

その章で最初に出る用語に説明が無ければ 1 文で補う。他章で説明済みなら章番号を添える。

- 「Pydantic（型注釈でデータの形を定義し、検証まで行う Python ライブラリ）」
- 「スニペット（検索エンジンが返す本文の抜粋）」
- 「toolUse（ツールを使うという宣言。第2章 2.1.2）」
- 「`maxTokens` に達しても例外は出ません（第1章 1.1.4）」

## 5. 読者の行動に繋がらない記述

**その文を消して、読者の次の行動が変わるか。変わらないなら消す。**

削除する。

- 書き手や開発チームの経験談（「開発中に落ちました」「一度間違えた点です」）。
  troubleshooting.md への参照だけ残す
- 教材の運営事情（「学習コストを抑えるため」「学習用の」）
- 読者が判断すべきことの代弁（「〜が分かります」「〜が効きます」「〜とはこのことです」）
- 教材で用意したものの説明のうち、読者の操作に関係しない部分

残す。範囲の宣言（「この教材は最後までオンデマンドだけで動きます」）、
既定値の明示、AWS 認証の要否（「モデルは呼びません」）は読者の行動を変える。

## 6. 表と箇条書き

- 表は列 3 つまで、セルは 20 字まで（コード識別子は除く）。超える説明は表の直後に段落で書く
- 箇条書きは独立した並列項目が 3 つ以上あるときだけ。1 項目 1〜2 行。
  3 行以上の説明が要る項目が混ざったら段落に切り替える。項目が 2 つなら段落の切れ目で足りる

## 7. 文体

- 敬体（です・ます）で統一する。段落の途中で常体に落とさない。
  箇条書きの中は、リスト全体で統一されていれば常体でよい
- 文の途中で改行しない。第1・2章は句読点で折り返し、第4章以降は 1 文 1 行

## 8. Python ファイルを直したあとの確認

exercises / solutions / 章直下スクリプト / verify の `.py` を変更したら、
リポジトリルートで Pyright を実行し、import の解決を確認する。
ルートの `pyrightconfig.json` が、章スクリプトの `sys.path.insert` と同じ探索パス
（`exercises/` / `target/` / `fixtures/` / `07-full-app`）をエディタ向けに宣言している。

```bash
uvx pyright --pythonpath <章>/.venv/bin/python <変更した .py ...>
```

- `reportMissingImports` が出たら直す。例外は第13章の `judges`（13.3.1 の cp で学習者が作るファイル）だけ
- `exercises/` を新しい場所から import する構造にしたら、`pyrightconfig.json` の
  `executionEnvironments` にその章の `extraPaths` を追加する
- 穴埋め前の `...`（EllipsisType）に対する型エラーと、verify やスクリプトが検証用に `None` を
  渡している箇所の型エラーは既知で、直す対象にしない
- 変更が解答例のコードなら、対応する章の `uv run pytest -q`（verify）が変更前と同じ結果になることも確認する

## 直さないもの

技術的な内容 / コード / コマンド / 章構成 / 数値 / バージョン / ファイルパス / 変数名。
モデルに渡るツール docstring の指示文（「要約はあなたの仕事」など）は、モデル向けの仕様なので残す。

内容の誤りを見つけたら、直さずに報告する。

## 出力

1. 変更点の一覧（箇所 / 変更前 → 変更後 / 分類）
2. 置き換えたが、元の語のほうが情報量が多かった箇所
3. 内容の誤り、前後の節との重複として気づいた点（直していないもの）
