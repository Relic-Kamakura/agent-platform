# 第3章 ツール設計

この章を終えると、規約に沿ったツールを 1 本ゼロから書けるようになります。
ハンズオンで `fetch_page`（ページ本文の取得）を実装し、docstring の質・エラーの返し方・
リトライの範囲まで機械判定にかけます。エージェントの品質はツールの質で決まるので、
この章がいちばん案件に直結します。

## 3.1 docstring はモデルに渡る仕様書

Strands の `@tool` は、関数のシグネチャと docstring から Converse API の
`toolSpec`（name / description / JSON Schema 形式の inputSchema）を生成し、
そのままモデルに渡します。docstring を読むのは同僚ではなくモデルです。
モデルはその文面だけで「いつ使うか」「何を渡すか」を決めます。

このリポジトリの規約は 3 節構成です。

- **受け取るもの** — 引数の意味と、やってはいけない渡し方（複数観点を 1 クエリに詰めない、など）
- **返すもの** — 成功時の形式と、失敗時の形式（`ERROR[...]` で始まる、など）
- **含まないもの** — このツールがやらないこと

3 つ目がいちばん効きます。モデルは docstring から「できそうなこと」を推測するので、
否定を明示しないと過剰な期待で誤用します。「ページを取得する」の 1 行だけだと、
ログインの背後にある社内ページにも使われ、JS レンダリングが必要なページの空応答を
「本文が空だった」と誤解されます。実物は `07-full-app/src/tools/web_search.py`。

## 3.2 1 ツール 1 責務

`search_and_summarize` のような複合ツールは作りません。束ねると次が起きます。

- 「検索だけしたい」場面で使えるツールが無く、結局ツールが増殖する
- 失敗時に検索と要約のどちらで失敗したか分からない
- 要約の質を直したいとき、処理がツールの中に埋まりプロンプトから手が届かない

原則は、判断はモデル側に・作業はツール側に。検索という作業はツールが行い、
結果の取捨と要約はモデルが判断します。

## 3.3 失敗を握りつぶすと、モデルは嘘をつく

ツール内で `except Exception: return ""` と書くと何が起きるか。モデルは空文字列を
「検索したが 0 件」と解釈し、足りない情報を推測で埋めて、もっともらしい報告を
書き上げます。ログには何も残らず、開発者は品質劣化の原因を追えません。二重に有害です。

このリポジトリの型（`src/errors.py`）:

- 例外に `retryable`（再試行に意味があるか）と `hint`（次に取るべき行動）を持たせる
- ツール層で `format_tool_error()` により `ERROR[...]` 形式の文字列にしてモデルへ返す
- 「retryable: no / 手持ちの情報でまとめてください」を読んだモデルは、
  でっち上げる代わりに「確認できず」と報告する方向へ切り替わる

## 3.4 リトライは範囲を絞る

外部 API は失敗する前提で書きますが、何でもリトライすればよいわけではありません。
`src/tools/providers/tavily.py` の方針:

- リトライするのは timeout / 429 / 5xx のみ（時間を置けば直る可能性がある）
- 403 や 404 などの 4xx は 1 回で諦める。何度呼んでも結果は同じ
- 間隔は指数バックオフ（1s → 2s → 4s）
- タイムアウト値とリトライ回数は config から注入する

返す量の設計もツールの責務です。生 HTML を丸ごと返すとコンテキストが毎ターン膨らみ、
トークン費用が跳ねます。ハンズオンの `fetch_page` に `max_chars` があるのはこのためです。

## 3.5 【ハンズオン】fetch_page を実装する

検索結果のスニペットでは足りないとき、出典 URL の本文を取得するツールを作ります。
`07-full-app/src/tools/fetch_page.py` を新規作成し、`build_fetch_page_tool(settings)` を
実装してください。

機能要件:

1. `fetch_page(url: str, max_chars: int = 4000) -> str`
2. httpx で GET し、本文テキストを max_chars で切り詰めて返す
3. `http://` / `https://` 以外の URL は取得を試みず `ERROR[` 形式で拒否する
4. タイムアウト値は `settings.http_timeout_seconds` から取る
5. timeout・5xx は `settings.http_max_retries` 回まで指数バックオフでリトライする
6. 失敗はすべて `ERROR[...]` 形式（retryable と next_action を含む）で返す。
   例外は `src/errors.py` に追加してよい

docstring 要件:

- 「受け取るもの」「返すもの」「含まないもの」の 3 節を含む
- 「含まないもの」に、JS 実行（動的レンダリング）をしないこと・認証が必要な
  ページは取得できないことを明記する

進め方は、先に判定テストを読むのが近道です。`03-tool-design/verify/test_fetch_page.py` が
要求仕様そのものになっています。

```bash
uv run --project 07-full-app pytest 03-tool-design/verify -q
```

`6 passed` で合格です。詰まったら `solutions/fetch_page.py` を見て構いません。

余裕があれば（要 AWS）、作ったツールを `02-first-agent/01_minimal_agent.py` に追加し、
「https://example.com の内容を要約して」で呼ばれることを確認してください。
