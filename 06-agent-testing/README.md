# 第6章 エージェントのテスト

この章を終えると、自分のツールに CI で回せるテストを書けるようになります。
ハンズオンは第3章で作った `fetch_page` に自分でテストを書くこと。
「何を固定すべきか」を自分で決めるところまでが課題です。

## 6.1 概要

### 6.1.1 なぜエージェントのテストは難しいか

モデルの応答は確率的で、同じ入力に同じ出力が返る保証がありません。
「期待値と一致すること」を前提とする assert は、モデルの出力に対しては書けない。
これがエージェントのテストが普通のコードと違う点です。

### 6.1.2 決定的な部分と確率的な部分を分ける

エージェントのコードには 2 種類の性質が同居しています。テスト戦略はここで分かれます。

- **決定的** — 設定の解決、ガードの発動、ツールの異常系、エージェント同士の結線。
  普通の pytest で固定できる（この章）
- **確率的** — モデルが良い報告を書けるか。assert では検証できない。
  evals の領分（第13章）

決定的な部分は、プロンプトをどれだけ書き換えても壊れてはいけない不変条件です。
それを普通のテストで固定し、確率的な部分だけを evals に回す。この分離が
エージェントを CI に載せるための前提になります。

## 6.2 実装のポイント

### 6.2.1 モデルを呼ばない 38 件

07-full-app のテストは 38 件、すべてモデルを呼びません。合計 1 秒未満・費用ゼロ・
CI に載ります。内訳:

- `test_config.py` — モデル ID の解決規則とバリデーション
- `test_guards.py` — 上限で止まり、理由がモデルに渡る形であること
- `test_web_search.py` — ツールの正常系・異常系・リトライ回数
- `test_agents.py` — Orchestrator のツール一覧と「Review がツールでない」こと

やりがちな失敗も挙げておきます。モデル応答をモックして、そのモックの中身を
assert するテスト。自分の書いたモックを検証しているだけで、何も守っていません。
カバレッジは増えますが、落ちることは永遠にない。

### 6.2.2 技法は 3 つ

**外部 API はモックする。** `test_web_search.py` では `httpx.Client` を偽クラスに
差し替え、timeout / 429 / 5xx / パース不能を再現します。リトライ回数まで assert する
のがこのリポジトリの流儀です（初回 + 2 回 = ちょうど 3 回で諦める）。
`time.sleep` も差し替えるので待ち時間はゼロ。

**AWS 認証情報は分離する。** `tests/conftest.py` がダミー認証情報を注入しています。
`BedrockModel` はコンストラクタで boto3 クライアントを作るため、エージェントを
組み立てるだけで認証情報の解決が走るからです。分離しないと、開発者のローカル設定
次第でテストが通ったり落ちたりします。開発中に `aws login` のプロファイルが原因で
実際に落ちました（troubleshooting.md 先頭に顛末）。

**ガードは hook を直接叩く。** `test_guards.py` はエージェントを動かしません。
イベントオブジェクトを手で作ってコールバックに渡せば、ループを回さずに
全分岐を検証できます。

### 6.2.3 テストは仕様書になる

ここまでの各章の verify/ は、要求仕様をテストで書いたものです。案件でも同じで、
「タイムアウトは 2 回リトライし、だめなら ERROR 形式で返す」をテストにしておけば、
プロンプトを頻繁に書き換える調整期でも、土台の無事を毎回 1 秒で確認できます。

## 6.3 【ハンズオン】fetch_page のテストを書く

`07-full-app/tests/test_fetch_page.py` を新規作成してください。
第3章の verify を写すのではなく、自分で観点を決めて書くこと。

要件:

1. テスト関数を 4 つ以上
2. 次の観点を含める
   - 正常系: 本文が返り、max_chars で切り詰められること
   - 異常系: 失敗時に `ERROR[` 形式で返ること（httpx をモックして再現する）
   - リトライ: 試行回数が設定どおりであること（`time.sleep` も差し替える）
3. LLM・実ネットワークを呼ばない
4. 既存の 38 件と一緒に全パスする

`test_web_search.py` の `_Client` パターンがそのまま使えます。`@tool` でラップされた
関数は `.__wrapped__` で素の関数を取り出せます。各テストに「このテストが落ちるのは
どんなバグが入ったときか」を 1 行コメントで書くと意図が明確になります。

```bash
uv run --project 07-full-app pytest 06-agent-testing/verify -q
```

判定内容はテストファイルの存在・関数数・モック使用に加えて、
書いたテストを実際に実行して通ることまで確認します。`4 passed` で合格です。

## 6.4 まとめ

エージェントのテストは非決定性と正面から戦いません。決定的な部分（設定・ガード・
ツール・結線）を普通の pytest で固定し、確率的な部分は evals（第13章）へ回します。
**書き換えるものと、壊れてはいけないもの**。この線引きがエージェントの
テスト戦略のすべてです。

書いた `test_fetch_page.py` は既存の 38 件と一緒に回し続けてください。
次章では、ここまで部分ごとに触ってきた完成形を通して読みます。
