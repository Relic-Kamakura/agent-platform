# 教材の文章ガイド

章を追加・改訂するときはこのガイドに従う。10 章以降を書く人（人間・AI とも）が対象。

出典: 技術書出版社が公開している LLM 向け技術文書ルール、AI 生成文のリライト術の記事、
および Diátaxis のチュートリアル設計原則を、このリポジトリ向けに要約したもの。

## 書いてはいけないもの

- 本文中の予告と総括。「この章では〜を扱う」「まとめると」「重要なのは〜である」。
  読めば分かることを宣言しない。章末の「まとめ」節だけは例外で、
  核心 1 段落 +「次に何をすべきか」を書く（下の「章の構成」参照）。
- 空虚な修飾。「強力な」「シームレスな」「鍵となる」「根本的な」「非常に」「劇的に」。
  形容詞を消しても意味が変わらないなら、その形容詞は要らない。
- 箇条書き・表・太字の乱用。「考え・因果」は段落で、「列挙できる事実・仕様値・手順」は
  箇条書きで書く。どちらかに偏らせない。太字は 1 ファイルに数カ所まで。
- 半端な箇条書き。箇条書きは独立した並列項目が 3 つ以上あるときだけ使い、
  1 項目は 1〜2 行に収める。3 行以上の説明が要る項目が混ざったら、箇条書きをやめて
  段落で書く。項目が 2 つなら段落の切れ目で足りる。
- 説明を詰め込んだ表。表は列 3 つまで、セルは 20 字まで（コード識別子は除く）。
  それを超える説明はセルから出し、表の直後に段落で書く。
- バージョンで変わる値の直書き。モデル ID・単価・コンテキストウィンドウ・最大出力・
  最小キャッシュ長・タイムアウト値・ライブラリのバージョンは docs/versions.md に置き、
  本文からは「versions.md を参照」で参照する。
- 長文の段落。1 段落は 2〜4 文まで。5 文を超えたら分割するか箇条書きに直す。
- 「〜しましょう」の連続。手順は命令形で書く（「実行する」「確認する」）。
- どの文も同じ長さ・同じ文末。です・ます が均一に並んだら書き直す。
- 網羅癖。「3 つのポイント」「4 つの特徴」のような、数を揃えるための列挙をしない。
  言うべきことが 2 つなら 2 つだけ書く。
- 命題型の見出し。「リトライは範囲を絞る」「失敗を隠すと、モデルは嘘をつく」のような
  主張文を見出しにしない。見出しはテーマの名前（名詞句）か、読者がそこで知りたいこと
  （「判定を取得できなかったとき」「どの失敗をリトライするか」）で立て、主張は本文で書く
  （詳細は .claude/skills/stop-ai-slop-jp）。
- 比喩と擬人化。「revise に倒す」「静かに壊れる」「握りつぶす」「刺さる」「効く」
  「寄せる」「潰す」「生やす」のような語を、起きていることの記述に置き換える
  （「revise 扱いにする」「例外は発生しないが品質が下がる」「例外を捕まえて何も返さない」）。
  「流す」「叩く」「回す」も「渡す」「呼ぶ」「実行する」に直す。判断に迷ったら置き換える
- 界隈でしか通じない省略。「型」（Python の型と紛らわしい）「生 HTML」「素の性能」など。
  一般語に置き換えるか、初出で 1 回だけ補足する
- 説明なしの初出用語。その章で最初に出る用語には 1 文の説明を付ける。
  他章で説明済みなら章番号を添える（「第1章 1.1.4 参照」）
- 読者の行動に繋がらない記述。書き手や開発チームの経験談（「開発中に落ちました」）、
  教材の運営事情（「学習コストを抑えるため」）、読者が判断すべきことの代弁
  （「〜が分かります」「〜が効きます」）。その文を消して読者の次の行動が変わらないなら消す
- 読者が補えない省略。主語や指示語（「これ」「この値」「土台」）の指す先が文中に無い文、
  「生で叩く」「握りつぶす」のような口語・比喩だけの説明を書かない。
  比喩を使うなら、その実体（何をどうすることか）を同じ文か直後に一句添える。
- 章の本質に関係ない説明。依存パッケージの内訳（「botocore[crt] も一緒に入ります」）、
  論文の著者名・出典年の律儀な併記（「Wei らの論文 2022」）、後の節・章の先取り予告
  （「実測は 1.5 で行います」「第3章で学ぶ規約の先取りです」）、操作の小ネタ
  （「戻すには git checkout」）。手を動かすのに必要な情報だけを書く。
- 文の途中での改行。Markdown は改行を半角スペースとして描画するため、
  「組み立てと 実行は」のように日本語の文中へ不要な空白が入る。
  段落内で折り返す場合は句点（。）の直後だけにする。

## 書くべきもの

- 最初に到達点。章の冒頭で「終えると何ができるようになるか」を具体的に示す。
  抽象的な学習目標ではなく、「〜が動く」「〜を自分で説明できる」の形で。
- 実測値と実体験。このリポジトリには本物の数字がある
  （コールドスタート 4 秒、テスト 36 件、8080 番ポートを Docker Desktop に取られた話）。
  一般論の代わりにこれを使う。
- 因果のメカニズム。「A するとよい」ではなく「A しないと B が起きる。なぜなら C そのため」。
- 期待される結果。手順の各ステップに「こうなるはずだ」を添える（Diátaxis）。
  読者は自分が正しい道にいるか、常に確認できる必要がある。
- 一本道。チュートリアル部分では選択肢を並べない。代替手段の議論は解説側に置くか消す。
- 一文だけの段落。長い説明のあとに短い一文を置くと、そこが読まれる。

## 章の構成

節の並びは全章で固定する。手本は `01-invoke-bedrock/README.md`。

1. 冒頭（見出しなし）— 到達点と、章のセットアップコマンド
2. `## N.1 概要` — その技術は何か・何を解決するか・全体の中の位置づけ。
   構造が伝わる場合は Mermaid 図を置く。仕様値は裏取り済みのものだけ書く
3. `## N.2 実装のポイント` — このリポジトリの実装・規約との対応。設計判断の理由はここ。
   内容が無い章（環境構築・通読の章）は省略してよい
4. `## N.x 【ハンズオン】...` — 手順
5. `## N.last まとめ` — 核心 1 段落。「結局これは何で、次に何をすべきか」
6. `## 次の章` — 次章へのリンク

- 見出しは `# 第N章 タイトル` → `## N.x 節` → `### N.x.y`
- 解説節（Diátaxis の explanation）とハンズオン節（tutorial）を同じ README に置くが混ぜない。
  解説は読み物、ハンズオンは命令形の手順 + コマンド
- コマンドはコピペしやすいよう 1 ブロック 1 実行単位。直後に「〜が出るはずです」と期待結果を書く
- 実行スクリプトは章ディレクトリ直下に `01_*.py` の連番で置く
- verify/: 合格条件のテスト表現。失敗メッセージには「README のどの節を読み直すべきか」を入れる
- ハンズオンは**穴埋め方式**を標準とする。章直下の `exercises/` に TODO 付きの
  骨組み（連番 `01_*.py`）を置き、学習者は TODO だけを実装して `uv run exercises/01_xxx.py`
  で実行する。TODO を埋める材料（コード構造・データの場所）は概要節に書き、
  ハンズオン節末に開閉式（`<details><summary>解答例</summary>`）の解答例を付ける。
  完成形は solutions/ に置き、verify は TODO の残存を検出して該当節へ誘導する
- ハンズオンは**章のディレクトリ内で完結させる**。編集・作成・実行するファイルは
  すべて章内に置き、本体 `07-full-app/` のコードは編集させず「読み比べの対象」にする
  （手本は第3章: 章内で自作 → 本体の完成品と読み比べ）。本体を改造する旧方式の章は
  穴埋め移行のときに章内完結へ改める
- 全章に適用済み（2026-08-24 移行完了）。例外は第7章（通読）と
  第9章（章 = CDK コード本体のため、TODO を埋め込まず「手順 + 解答例」形式）
- どの章も「学習者がコードを書く」工程を必ず含める。読んで答えるだけの章を作らない

## 推敲チェック

書き終えたら次を確認する。

1. 冒頭 3 行だけ読んで、何ができるようになる章か分かるか
1. 仕様値・数値に裏取り（一次情報 or 実測）があるか。無いものは書かない
2. 箇条書きを 2 つ以上、段落に書き直せないか
3. 「重要」「ポイント」「しっかり」を検索して全部消せないか
4. 実測値・実例がひとつも無いセクションはないか
5. 音読して、文末が 3 連続で同じになっていないか
