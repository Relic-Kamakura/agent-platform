# 学習ロードマップ

この教材で「何を・どの順で」身につけるかの計画。育成の進捗管理にもこの表を使う。
**実体はルート直下の章ディレクトリ**（README.md の章一覧参照）。本表の項目と章の対応:

| Tier 項目 | 章 |
| --- | --- |
| 1-1 エージェントループ | 02-first-agent |
| 1-2 ツール設計 | 03-tool-design |
| 1-3 マルチエージェント | 05-multi-agent |
| 1-4 セーフガード | 04-cost-control |
| 1-5 エラー設計 | 03-tool-design |
| 1-6 テスト | 06-agent-testing |
| 1-7 認証・認可 / 基盤 | 01-invoke-bedrock, 08-agentcore-deploy, 09-infra-as-code（+ 10-auth 予定） |
| 1-8 評価 | 12-evaluation |
| 1-9 インジェクション耐性 | 13-security |
| 1-10 ストリーミング | 11-frontend |
| Tier 2 各項目 | 14-mcp / 15-prompt-caching / 16-guardrails / 17-hitl / 18-structured-output |
| Tier 3 各項目 | 99-appendix（入口ドキュメント） |

- 対象: エージェント開発案件への参画を目指す部内メンバー（G4）
- ゴール: Tier 1 で案件に参画できる。Tier 2 で単独で手が動く。Tier 3 は案件要件に応じて
- 各項目に**習得判定**を付けている。「読んだ」ではなく「できた」で判定する

## 用語の整理（先に読むこと）

学習項目としてよく挙がる言葉と、このリポジトリの対応関係。

| 言葉 | 実体 | このリポジトリでは |
| --- | --- | --- |
| ReAct | 推論→ツール実行→観察を繰り返すエージェントの基本ループ | Strands の Agent がまさにこれ。`orchestrator.py` の動作ログでループが観察できる |
| CoT (Chain of Thought) | 問題を思考ステップに分解させるプロンプト技法 | Orchestrator の「観点に分解してから調べる」システムプロンプトが該当 |
| セーフガード（アプリ層） | ツール上限・ターン上限などコードで掛ける制御 | `src/guards.py` に実装済み |
| ガードレール（マネージド層） | Bedrock Guardrails。入出力のフィルタリング | 未実装（Tier 2） |
| RAG / Knowledge Bases | 外部知識の検索拡張生成。KB は AWS のマネージド RAG | 対象外（Tier 3。別モジュールとして学ぶ） |
| プロンプトマネジメント | プロンプトの版管理と、変更時の退行検知 | 本質は「Git で版管理 + evals で退行検知」。ツール（Bedrock Prompt Management）はその後 |
| HITL (Human-in-the-Loop) | エージェントの判断に人間の承認を挟む設計 | 未実装だが、実装基盤（`BeforeToolCallEvent` hook）は済み（Tier 2 演習） |

## Tier 1: この教材の本編で習得する（案件参画の必須ライン）

| # | 項目 | 学び方 | 習得判定 |
| --- | --- | --- | --- |
| 1-1 | エージェントループ（ReAct）の理解 | architecture.md の「このコードのどこが ReAct か」を読み、実行ログでループを追う | ログを見て「いまどのターンで何が起きたか」を説明できる |
| 1-2 | ツール設計（1責務 / docstring = LLM 向け仕様書） | `src/tools/web_search.py` を読み、演習でツールを 1 つ追加する | 追加ツールがレビュー規約（受け取る/返す/含まない）を満たす |
| 1-3 | マルチエージェント設計判断 | `orchestrator.py` / `review_agent.py` の「どこを裁量に任せ、どこを固定するか」のコメントを読む | Search がツールで Review が決定的実行である理由を説明できる |
| 1-4 | コスト・暴走対策（アプリ層セーフガード） | `src/guards.py` と `tests/test_guards.py`。演習で上限値を変えて挙動を観察 | 上限超過時にエージェントへ何が返るかを説明できる |
| 1-5 | エラー設計 | `src/errors.py`。retryable / hint の思想 | ツール失敗を握りつぶすコードの何が問題かを説明できる |
| 1-6 | LLM を呼ばないテスト | `tests/` 一式と `conftest.py` の認証分離 | 自作ツールに異常系テストを書ける |
| 1-7 | 認証・認可（IAM 実行ロール / JWT） | Phase 2–3 の CDK コード（実行ロールの信頼ポリシー、JWT authorizer、Cognito） | Runtime 実行ロールに必要な最小権限を列挙できる |
| 1-8 | 評価とプロンプトマネジメントの基礎 | Phase 5 の evals。ケース作成→実行→失敗分析→プロンプト修正→再実行を一周 | プロンプト変更の前後で eval を回し、退行の有無を報告できる |
| 1-9 | プロンプトインジェクション耐性 | mock プロバイダの注入 fixture + 耐性 eval（Phase 5 で追加） | 「検索結果は信頼できない入力である」を設計に反映できる |
| 1-10 | ストリーミング応答 | Phase 4 のフロントエンド実装 | ストリーミングの有無で UX とタイムアウト設計がどう変わるか説明できる |

## Tier 2: v1 完了後、このリポジトリの拡張で学ぶ（推奨・2〜3 か月）

| # | 項目 | 学び方 | 習得判定 |
| --- | --- | --- | --- |
| 2-1 | MCP サーバ | 演習: `web_search` を MCP サーバとして切り出し、Strands の MCP クライアントで接続し直す | 自作 MCP サーバをエージェントから呼べる |
| 2-2 | プロンプトキャッシュ | `BedrockModel` の `cache_config` を有効化し、eval のコスト集計で前後比較する | キャッシュヒット時のコスト差を実測値で示せる |
| 2-3 | Bedrock Guardrails（マネージド層） | Guardrail を CDK で定義し `BedrockConfig.guardrail_id` で接続 | アプリ層ガードとの役割分担を説明できる |
| 2-4 | HITL（承認ゲート） | 演習: `BeforeToolCallEvent` で「書き込み系ツールは人間の承認待ち」を実装 | 承認/否認の両パスをテストで示せる |
| 2-5 | 構造化出力 | 演習: ReviewAgent の `VERDICT:` テキストパースを `structured_output_model` に置き換える | パース失敗という故障モードが消えたことを説明できる |

## 教材の外で補う領域

教材だけでは育たないもの。案件 OJT とセットで計画する。

- **非決定性の顧客説明**: 「100% は保証できないが eval で継続測定する」という合意の取り方、デモ失敗時の切り分け説明
- **本番運用**: 実トラフィックでの失敗分析、モデルバージョン更新への追従

## 資格との接続

用語の網羅は資格学習に任せ、本教材は「作って身につける」に徹する。
Tier 2 まで消化したメンバーには **AWS Certified Generative AI Developer - Professional (AIP-C01)** の受験を推奨する。出題範囲（ReAct / CoT / HITL / Guardrails / KB / Prompt Management）が本ロードマップとほぼ対応しており、知識の穴を検出できる。
