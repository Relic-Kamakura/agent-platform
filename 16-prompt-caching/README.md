# 第16章 プロンプトキャッシュ

この章を終えると、プロンプトキャッシュ付きのエージェントを自分で組み立て、2 回目の呼び出しでキャッシュ読み取りが計上される様子を実測できるようになります。
どんなプロンプト構造なら再利用されるのか（されないのか）も説明できるようになります。

この章も独立した uv プロジェクトです。最初に依存を入れてください。

```bash
cd 16-prompt-caching
uv sync
```

## 16.1 概要

### 16.1.1 何を解決するか

モデルの API はステートレスで、エージェントはループのたびにシステムプロンプトとツール定義、会話履歴の全体を再送します（第2章）。
つまりターンが進むほど、同じ前半部分を毎回フルコストで処理し直すことになります。
この重複処理を減らすのがプロンプトキャッシュで、前回と重なる部分の処理結果をモデル側が再利用し、その分の課金を下げる仕組みです。

### 16.1.2 前方一致の仕組み

仕組みは前方一致です。リクエストの先頭からの並びが前回と一致した部分は、モデル側が処理済みの状態を再利用し、大幅に安い単価で課金されます。
裏を返すと、先頭に 1 バイトでも差が入ると、それ以降は全部キャッシュミスです。

エージェントと相性が良い理由も構造から分かります。
ループの各ターンは「前回までの内容 + 新しいツール結果」なので、前半は毎回同じ。まさに前方一致でキャッシュが再利用される形をしています。

キャッシュが再利用されなくなる典型例も知っておいてください。

- システムプロンプトに現在時刻やリクエスト ID を埋め込む（毎回先頭が変わる）
- ツール定義の順序が実行のたびに変わる（set から生成している等）
- ターンの途中でモデルやツール構成を切り替える

### 16.1.3 課金と最小プロンプト長

キャッシュの課金は非対称です。
書き込み（初回）は通常の入力より割増になり、読み取り（2 回目以降）は通常の入力より安くなります。係数はモデルごとに違うため、Bedrock の料金表で確認してください。
1 往復で終わる呼び出しでは割増だけを払って終わることもあり、有効化すれば必ず安くなるわけではありません。

もうひとつ、モデルごとに最小キャッシュ長があります。
先頭部分がその長さに満たないと、エラーにはならず黙ってキャッシュされません。
この章の既定モデル Haiku 4.5 の最小長は 4096 トークンで、ハンズオンの題材に長い調査ガイドラインを使うのはこのためです。

## 16.2 実装のポイント

Strands では `BedrockModel` に `cache_config` を渡すと有効になります。

```python
from strands.models import BedrockModel, CacheConfig

model = BedrockModel(
    region_name=region_name,
    model_id=model_id,
    max_tokens=1024,
    cache_config=CacheConfig(strategy="auto"),
)
```

`strategy="auto"` はキャッシュポイントの配置を Strands に任せる指定で、まずこれを使います。
`strategy="anthropic"` は配置や保持時間（`ttl`）を自分で制御したいときの指定です。

有効化はこの 1 行ですが、効くかどうかは 16.1.2 のとおりプロンプトの構造で決まります。
システムプロンプトを固定文字列に保ち、動的な値を混ぜない設計判断のほうが本体です。

効いたかどうかは `result.metrics.accumulated_usage` で確認できます。
キャッシュに書いたトークン数が `cacheWriteInputTokens`、キャッシュから読んだトークン数が `cacheReadInputTokens` に入ります（キャッシュが動いたときだけ現れるキーです）。

## 16.3 【ハンズオン】キャッシュ付きエージェントを組む

長い固定の調査ガイドラインをシステムプロンプトに持つエージェントを組み、同じ質問を 2 回投げてキャッシュの動きを実測します。
編集するのは `exercises/cached_agent.py` の 1 ファイルだけです。

### 16.3.1 TODO を 2 つ埋める

`exercises/cached_agent.py` を開いてください。
システムプロンプト `RESEARCH_GUIDE`（最小キャッシュ長を超える長さの固定文字列）は書いてあり、`build_cached_agent` に TODO が 2 つ残っています。

1. `cache_config=CacheConfig(strategy="auto")` を渡した `BedrockModel` を作る（16.2 のコードの形）
2. その model と `system_prompt=RESEARCH_GUIDE` で `Agent` を組み立てて返す

`RESEARCH_GUIDE` はそのまま渡してください。
現在時刻などを先頭に足すと、毎回先頭が変わってすべてキャッシュミスになります（16.1.2）。

### 16.3.2 合格判定

実装できたら TODO コメントを消し、判定を流します。

```bash
uv run pytest -q
```

`4 passed` で合格です。
モデルは呼ばず、cache_config が渡っていること・引数がそのまま使われていること・ガイドラインが変更なしで渡っていることを検査します。

<details>
<summary>解答例</summary>

```python
def build_cached_agent(model_id: str, region_name: str) -> Agent:
    """プロンプトキャッシュを有効にしたエージェントを組み立てる。"""
    model = BedrockModel(
        region_name=region_name,
        model_id=model_id,
        max_tokens=1024,
        # strategy="auto": キャッシュポイントの配置を Strands に任せる
        cache_config=CacheConfig(strategy="auto"),
    )
    # RESEARCH_GUIDE をそのまま渡す。現在時刻などを足すと毎回先頭が変わり、
    # すべてキャッシュミスになる（16.1.2）
    return Agent(model=model, system_prompt=RESEARCH_GUIDE)
```

全文は `solutions/cached_agent.py` にあります。

</details>

### 16.3.3 キャッシュ読み取りを実測する

組んだエージェントで同じ質問を 2 回投げ、usage を比べます（編集不要。Bedrock を呼びます）。

```bash
uv run 01_measure_cache.py
```

1 回目は `cacheWriteInputTokens` にガイドライン分のトークンが計上され、`cacheReadInputTokens` は 0 のはずです。
2 回目は逆に、`cacheReadInputTokens` に計上されます。
2 回目の入力の大部分が、割増の書き込みから安価な読み取りに変わったということです。

余裕があれば、`RESEARCH_GUIDE` の先頭に 1 文字足して再実行してください。
2 回目もキャッシュ読み取りが 0 のままになり、16.1.2 の「先頭 1 バイトの差」を実測で確認できます（確認後は元に戻すこと）。

## 16.4 まとめ

プロンプトキャッシュは「先頭からの並びが前回と一致した部分だけ安くなる」という規則で動き、再利用されるかどうかはプロンプトの構造で決まります。
有効化は `cache_config` の 1 行でも、システムプロンプトを固定文字列に保つ設計判断のほうが本体です。
効果は必ず `cacheReadInputTokens` の実測で確かめてください。書き込み割増がある以上、構造が悪ければ有効化がコスト増にもなり得ます。
